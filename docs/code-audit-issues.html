Persistence & data integrity 4 issues

StatePersister.save is fire-and-forget — callers never await durability

P1
main · state

Mutators across ShelfStore, ClipboardStore, PreferencesStore, SyncStore, and TeamStore all call persister.save(state) and return immediately. The write is queued via writeQueue but the caller can't observe success/failure. whenIdle() exists but is only used at quit-time (index.ts:506); per-mutation durability is never asserted.

Risk: a crash between mutation and the next coalesced flush silently drops the change. The toast throttling (PERSISTENCE_ERROR_TOAST_THROTTLE_MS = 30_000) further masks the loss because the error toast is also the user-visible signal.

// src/main/services/state/shelfStore.ts
replacePersonalLiveShelf(shelf: ShelfRecord): void {
  const state = this.getState()
  state.liveShelf = shelf
  this.persister.save(state)   // <-- void return, no await
}

Fix: have each domain mutator return a Promise<void> derived from persister.whenIdle() after enqueueing; IPC handlers can await it for write-confirm semantics on user-visible actions.

Stale state.json.tmp-* siblings are never recovered on startup

P2
main · state

StatePersister.save() writes to {statePath}.tmp-{pid}-{ts}-{rand} then renames. If the process dies after the write but before the rename, the temp file is orphaned. load() (persister.ts:92) reads only statePath — the most recent tmp sibling is silently ignored, even though it may be the user's latest intended snapshot.

// src/main/services/state/persister.ts
const tempPath = `${this.statePath}.tmp-${process.pid}-${Date.now()}-${Math.random().toString(36).slice(2, 8)}`
await fs.writeFile(tempPath, serialized, 'utf8')
// ...
await fs.rename(tempPath, this.statePath)

Fix: in load(), if the canonical file is missing, scan for *.tmp-* siblings, pick the newest by mtime, validate with the same Zod slice chain, and rename it into place. If canonical exists but a tmp is newer, log a warning and quarantine the tmp.

Migration reset can silently drop user data when a single slice fails

P2
main · state

migratePersistedState() (persister.ts:266) uses safeParse per slice and falls back to defaults for any failure. The fix in commit 1102179 improved isolation, but a corrupt preferences slice still resets the entire preferences record, including the user's plan, shortcuts, and onboarding completion. The user gets a working shelf back but loses all configuration silently.

Fix: surface a per-slice fallback toast and persist a "degraded slice" marker so Settings → General can show "we reset your preferences because the saved file was unreadable."

Directory-fsync is best-effort and silently swallows macOS-specific errors

P3
main · state

persister.ts:149-157 opens the parent directory and calls handle.sync() wrapped in try { } catch {}. On macOS the call returns success without actually fsyncing on some filesystems (HFS+/APFS quirks); a true ENOSPC or EACCES here would also be silently swallowed, hiding a real durability failure.

Fix: at minimum log at console.warn; ideally branch on process.platform and only attempt the dir fsync on platforms that report success meaningfully.

Single-instance & native IPC 3 issues

startSingleInstanceWatch depends on fs.watch for a critical signal

P0
main · single-instance

The whole "second launch resurfaces Settings" UX rides on Node's fs.watch observing a marker file in app.getPath('userData'). macOS's FSEvents does not guarantee sub-second delivery, can coalesce bursts (login-item races), and is known to drop events under heavy I/O on the parent directory. The comment at singleInstance.ts:80-82 already acknowledges rename can emit twice.

Real-world impact: a user double-clicking the app while Ledge is running expects the Settings window to appear. Under load (sync push, state write) the event can be lost; the secondary instance just quits without surfacing anything.

// src/main/services/singleInstance.ts
watcher = watch(userDataDir, { persistent: false }, (_event, filename) => {
  if (filename !== SECOND_INSTANCE_MARKER_FILENAME) {
    return
  }
  rmSync(markerPath(userDataDir), { force: true })
  onSignal()
})

Fix options: (1) move the resurface signal into the Swift helper over the existing XPC-style stdin/stdout protocol; (2) poll on a 100–200ms interval as a fallback to the watcher; (3) keep the watcher but additionally have the secondary instance send a UDP/Unix-domain datagram to a known socket.

startSingleInstanceWatch can call onSignal after unsubscribe

P1
main · single-instance

The unsubscribe fn returned at singleInstance.ts:92 calls watcher.close(). Node's fs.watch close is async; a callback already in the event-queue can fire after unsubscribe. onSignal then calls preferencesWindow.show() on a destroyed window during quit.

Fix: guard the callback with an unsubscribed flag and early-return, or wrap onSignal() in a try/catch with a webContents.isDestroyed() check.

NativeAgentClient circuit-breaker trip logs once and never recovers

P1
main · native agent

When the Swift helper exits unexpectedly several times in a row, the client trips a circuit breaker and emits one statusChanged event. Once tripped, it stops auto-restarting. The clipboard monitor falls back to the JS poller (good), but the shake gesture and bookmark resolution are gone for the rest of the session, and no UI surface tells the user.

Fix: add a half-open recovery probe after a cool-down (e.g. 60s), surface a status pill in Settings → General, and reset the counter when the helper stays up for >5 min.

Convex backend 4 issues

convex/sync.ts exposes several public mutations that should likely be internalMutation

P1
convex

sync.ts exports registerDevice, upsertShelf, deleteShelf, patchPreferences, authorizeImageUpload, abandonImageUpload, recordImageAsset, recordSyncEvent, upsertShelfItem, and deleteShelfItem as mutation. Per the project's convex/_generated/ai/guidelines.md, anything that touches billing/storage caps, deletes other users' data, or is only ever invoked by an authenticated server-side flow should be internalMutation.

Risk: a leaked Convex deploy URL or a renderer compromise can hit these directly. authorizeImageUpload + recordImageAsset are the storage-billing surface; patchPreferences mutates another user's preferences if userId is passed (see #10).

Fix: convert to internalMutation and route renderer→Convex calls through an httpAction in convex/http.ts that does the auth check and forwards. The registerDevice flow is a likely exception because new users have no auth yet — leave that public but rate-limit it.

convex/auth.ts and convex/teams.ts accept user identifiers as arguments in some places

P1
convex

sync.ts:patchPreferences, upsertShelf, deleteShelf, upsertShelfItem, and deleteShelfItem all take a userId / deviceId arg and trust it as the owner. Convex's ctx.auth.getUserIdentity() exists; cross-user writes are trivially possible until the args are replaced with the identity subject.

Fix: derive userId from ctx.auth.getUserIdentity() server-side and drop the arg. For unauthenticated flows (device registration), gate by a signed install token.

convex/email.ts is missing "use node"; for an action that may need Node built-ins

P2
convex

Resend SDK + the RESEND_API_KEY flow described in AGENTS.md typically pulls in Node-only modules (crypto, fetch polyfills). Without "use node"; at the top of the file, Convex runs it in the V8 isolate where imports can silently fail at deploy time.

Fix: add "use node"; as the very first line of convex/email.ts.

Security & IPC surface 4 issues

Several IPC handlers use schema.parse(input) — a bad payload throws and the renderer's promise hangs

P1
main · ipc

ipc.ts mixes safeParse (good, returns a result) with schema.parse(input) (throws ZodError). When a .parse call throws inside an ipcMain.handle async callback, Electron rejects the renderer's ipcRenderer.invoke with an unhandled error and the renderer hook never resolves. Some handlers (e.g. restoreShelf, addPayload, addPayloads) wrap the throw into a returned Error, but several do not.

// src/main/ipc.ts (representative)
ipcMain.handle(IPC_CHANNELS.createShelf, async (_event, input: unknown) => {
  const parsed = createShelfInputSchema.parse(input)  // throws → renderer hang
  ...
})

Fix: convert every parse(...) in handler bodies to safeParse(...) and return a tagged result { ok: false, error }; or wrap each handler in a single withSchema(schema, fn) helper that catches and shapes the error.

lockDownWebContents is good but not applied to every window

P1
main · web-security

Test coverage (webSecurity.test.ts) verifies the helper's behavior in isolation, but a code search for callers of lockDownWebContents in the main process returned only the test file — there's no obvious call site in index.ts or the windows/ directory. Either the helper is invoked indirectly (worth a comment to confirm) or it's not actually wired into every BrowserWindow.

Fix: grep for the call site; if missing, call it from loadRenderer.ts for every renderer window before the first navigation.

Asset protocol allowlist uses path.startsWith for live items — symlinks inside the assets dir still pass lexical check on one branch

P2
main · asset

resolveAllowedAssetPath correctly uses realpathSync for the assetsDir branch (good — defends against planted symlinks). The live-items branch, however, does a lexical resolvePath(itemPath) === normalizedPath equality. If a shelf item's fileRef points to a symlink (legal on macOS), the renderer can request the symlink target instead and serve that file outside the live shelf.

// src/main/services/assetPathResolver.ts
for (const item of context.liveItems) {
  ...
  if (itemPath && resolvePath(itemPath) === normalizedPath) {
    return normalizedPath   // no realpath guard here
  }
}

Fix: in the live-items branch, additionally realpathSync the candidate and require the resolved target to equal one of the live items' realpathSync(getFileBackedPath(...)).

Tests & developer experience 3 issues

singleInstance.test.ts › invokes onSignal when the marker appears and stops after unsubscribe — 5s timeout, deterministic

P1
tests

The test relies on fs.watch firing its 'rename' event after the secondary writeSecondInstanceMarker() finishes. Under load (CI runners with cold caches) the FSEvents delivery can exceed 5s and the test fails with no actionable diff. The test passes locally but flakes in CI.

Fix: use fs.watch's recursive: true on macOS, or replace the watcher with a polling loop in the test fixture. Alternatively, inject a clock-advanceable signal channel for unit tests and keep fs.watch only in production.

User-story harness stderr noise: "Failed to persist Ledge state. ENOENT: rename…state.json.tmp"

P2
tests

Documented in src/main/services/__harness__/userStoryHarness.test.ts. The harness rapidly creates and destroys StateStore instances; the queued tmp-then-rename can race with the next teardown and fs.rename errors with ENOENT. Cosmetic but it makes legitimate failures hard to spot.

Fix: in the harness, await stateStore.whenIdle() before disposing, or give StatePersister a dispose() that drains the queue and refuses new writes.
